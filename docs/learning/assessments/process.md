# Assessment Process

This page describes how ERRSA reviews role readiness and records results. **Learning modules teach the material; assessment pages test the decisions a staff member would make.** They are separate sections on purpose.

## Which Assessment Applies?

| Track | Assessment | Current status |
| --- | --- | --- |
| Moderator | [Moderator Assessment](moderator.md){ data-preview } | Readiness exercise; any mandatory requirement is decided by the Server Lead |
| Admin | [Admin Assessment](admin.md){ data-preview } | **Required before new Admin promotion**, alongside supervised practice |
| Developer | [Developer Assessment](developer.md){ data-preview } | Provisional; Developer track and rubric require approval |

A candidate should understand the lower-role training relevant to the position. Completing an assessment demonstrates readiness; **it does not guarantee promotion or automatically grant permissions**. The Server Lead makes the final promotion decision under [Staff Advancement & Governance](../../documentation/6-staff-advancement-and-governance.md){ data-preview }.

## Steps for a Role Assessment

1. **Finish the relevant modules.** The supervisor confirms the trainee can navigate the source procedures, not merely recite commands.
2. **Discuss the scenarios.** An experienced staff member for the assessed role (or the Server Lead) checks the trainee's reasoning and evidence standards.
3. **Demonstrate practical skills where required.** Admin candidates complete controlled exercises with an experienced Admin or Server Lead. Never use unrelated player accounts or live property for training.
4. **Document results privately.** The supervisor records each exercise, what was demonstrated, gaps, and the date in approved staff storage—not on this wiki.
5. **Make the decision.** The Server Lead reviews the evidence of readiness, approves or requests further practice, and decides whether to promote.

## Required Admin Practical Exercises

Use a test area and consenting test players. Mark each result **Demonstrated**, **Needs practice**, or **Not yet tested**:

| Exercise | What to verify |
| --- | --- |
| CoreProtect chest history | Correct chest, timestamps, page navigation, and limits of what logs prove |
| Rollback safety | Scope a preview, recognize collateral changes, and demonstrate `/co cancel` |
| Controlled test rollback | Supervised `/co apply` only after verifying scope and authorization; check final build |
| Claim inspection | Use the **wooden hoe**; interpret claim owner, trust, and chest access |
| spark diagnostics | Explain a `/spark tps` reading, MSPT, and the difference from client FPS |
| Jail and release | Demonstrate a consenting test account, explain when each type of jail is permitted, and verify release |
| Incident coordination | Identify when a Developer or Server Lead must take over |

A candidate without Admin permissions must use an approved test environment or temporary supervised access **explicitly approved by the Server Lead**. Any temporary access must be removed and its removal verified after the exercise.

## Internal Training Record — Server Lead / Reviewers

Make one **private record per candidate**. Do not publish filled-out records, evidence, or personal notes in the wiki. The reviewer/Server Lead should document:

| Field | What to record |
| --- | --- |
| Candidate and role | Minecraft username, current role, role being assessed |
| Training | Relevant learning modules completed; date |
| Scenario results | Demonstrated / Needs practice / Not yet tested; brief observations |
| Practical results | Individual exercises, reviewer name/date, evidence references |
| Temporary access | Approval, permissions issued, issue/removal times, removal verification |
| Decision | Reviewer recommendation, Server Lead decision/date, outstanding training |
| Separate authorizations | Any independent restoration or complex item recovery authorization, scope, approver, and date |

!!! danger "Training does not automatically authorize recovery"
    Successful Admin assessment does **not** automatically grant independent CoreProtect rollbacks or complex inventory reconstruction. The Server Lead must separately authorize independent rollback work after supervised practice. Complex item recovery additionally requires an approved recovery procedure and explicit authorization.

## Retakes and Follow-Up

When an exercise is uncertain, record **Needs practice**, explain the gap and arrange a follow-up demonstration. Do not mark the assessment complete based only on written answers when supervised practice is required.
